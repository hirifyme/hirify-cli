# Приёмка: архитектурный аудит CLI

- Источник: запрос оператора от 17.09.2026 на полное архитектурное и кодовое ревью production CLI без изменения кода; последующее уточнение размещать документацию по назначению.
- Среда: local, публичные официальные источники. Мутации: только временные фикстуры и файлы независимой приёмки вне репозитория. Не входить в реальные аккаунты, не отправлять отклики, не публиковать и не менять код продукта.
- Объект: `docs/product/cli/architecture-audit.md` на переданном коммите.

## Критерии

1. `eco worktree verify` подтверждает отдельное дерево на переданном коммите. Diff коммита содержит только отчет и эту спецификацию.
2. Отчет различает рабочее дерево, зафиксированный публичный main, опубликованный npm-архив и незакоммиченный кандидат. Проверить SHA, имя пакета, версию, совпадение архива и исходников доступными read-only средствами. Имя `hirify-cli` не объявлено дефектом: оператор подтвердил, что имя `hirify` в npm недоступно.
3. Проверить покрытие каждого направления запроса: authentication, redirect/token/config/log security, Windows/macOS/Linux, headless и агенты, browser launch, ошибки/exit/diagnostics, сеть/retries/proxy/TLS/cancellation, installation/update/rollback, distribution/dependencies, concurrency/compatibility, tests/CI/releases/history, README/help/skill, границы модулей.
4. Для каждого finding есть файл и строки зафиксированного состояния, статус доказательства, пользовательский сценарий, severity/вероятность/confidence/blast radius, применимая практика, целевое решение и проверка с платформами. Выборочно проверить ссылки минимум у 8 наиболее серьёзных выводов и 4 выводов из других областей; опровергать преувеличения.
5. Независимо воспроизвести минимум 4 новых дефекта из отчета локальными заглушками и вымышленными токенами. Включить `logout --help`, разбор аргументов, неверный успешный ответ API и один сценарий credentials/concurrency. Можно читать авторский воспроизводитель, но не считать его JSON доказательством без запуска/проверки. Если использован существующий probe, изменить одну проверяемую фикстуру и показать, что наблюдаемый результат изменяется.
6. Проверить, что источники нормативных и сравнительных выводов первичные, а нормативные требования не смешаны с рекомендациями автора; как минимум OAuth loopback, proxy Node, credential storage и release dependencies. Невыполненная Windows/macOS-проверка не названа успешной; отсутствующая telemetry не названа установленной утечкой.
7. Отчет содержит карту текущей и целевой архитектуры, ответственности модулей, упорядоченную миграцию, test matrix, исполняемые acceptance criteria, риски и rollback, раздел о сохранении работающих решений и отдельные действительно продуктовые вопросы. План сохраняет имя пакета/команды и известные exit codes, описывает совместимость `--json` и auth state.
8. Доказательства доступны вне git, секретов реальных пользователей нет. Итоговый вердикт и evidence сохраняются по правилам `qa-verify` вне репозитория. Тексты CLI и исходники продукта не изменены.

9. Проверить критический проход (§14): добавленные доказательства соответствуют фактическому P-коду; план не требует keychain/device flow/multi-profile или смены Node floor без выбора. Есть явная граница смешанной конкурентности 0.4.7/новый store и совместимый rollback; новый lock не объявлен защитой от старого writer. Проверить отсутствие противоречий между findings, архитектурой, migration и acceptance.
